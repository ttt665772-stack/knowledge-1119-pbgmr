先定位问题：网络排查从“可复现”开始

网络故障最怕“时好时坏”。开始排查前，用 3 分钟记录 4 个要素：故障现象、发生时间、影响范围、最近变更。把“打不开网页”细化为“Wi-Fi 满格但浏览器 20 秒超时”，把“全公司断网”细化为“仅 5 楼 12 台有线终端无法获取地址”。可复现的故障，排查效率通常能提高 50% 以上；不可复现时，先做持续监测而不是反复重启设备。

第 1 步：分层确认，先排除“终端自身”问题

步骤 1：确认物理与链路状态。有线终端看网口灯是否常亮/闪烁，无线终端看是否连上正确 SSID。常见错误是连到了访客网络或 2.4G 弱信号频段，导致“能连不能通”。

步骤 2：检查本机地址。Windows 用 ipconfig /all，macOS/Linux 用 ifconfig 或 ip addr。重点看是否拿到 169.254.x.x 这类自动私有地址，出现即说明 DHCP 失败。若手动配置了静态地址，核对网关与子网掩码是否在同一网段。

步骤 3：分段测试连通性。按“网关 → 同网段其他主机 → 公网 IP → 域名”的顺序 ping。能 ping 通 IP 但打不开域名，问题多在 DNS；网关都 ping 不通，先查本机防火墙、VLAN 划分和交换机端口。单次排查控制在 10 分钟内，避免在终端侧反复重装驱动。

第 2 步：查 DNS 与网关，解决“能上 QQ 打不开网页”

这类现象 80% 与 DNS 有关。先执行 nslookup 目标域名，对比默认 DNS 与公共 DNS 的返回结果；若默认 DNS 超时或返回错误地址，临时切换 DNS 验证。企业环境还要检查 DNS 转发器、内网域名解析和 hosts 文件是否被篡改。

常见错误：只改一台机器的 DNS 就下结论；忽略 DNS 缓存（Windows 可执行 ipconfig /flushdns）；把代理软件残留的虚拟网卡当成真实网卡。建议同时检查系统代理设置与浏览器插件，代理配置错误造成的“断网”在办公场景中占比不低。

网关侧重点看 ARP 表与 MAC 地址冲突。若同一 IP 对应两个 MAC，或网关 ARP 频繁抖动，可能是地址冲突或环路。小型网络可在 15 分钟内通过逐段拔插网线定位环路；中大型网络查看交换机日志与端口流量更高效。

第 3 步：抓包与日志，定位“间歇性丢包/高延迟”

步骤 1：持续监测。用 ping 加时间戳连续测试 5–10 分钟，统计丢包率与延迟分布。丢包率低于 1% 但业务卡顿，优先查无线干扰、双工不匹配和上联带宽拥塞。

步骤 2：抓包对比。在终端和网关两侧同时抓包，看请求是否发出、响应是否返回。若终端发出 SYN 但无 SYN-ACK，问题在路径或目标端口；若双方都有包但应用仍失败，查 TLS 证书、MTU 和防火墙策略。

步骤 3：查设备日志。交换机看端口错包、CRC 增长和 STP 变更；路由器看 NAT 会话数与 CPU；无线控制器看终端漫游与信道利用率。把日志时间与故障时间对齐，误差控制在 1 分钟内，否则容易误判。

成本提示：一次上门排查的人工与停机成本常在 200–800 元/小时区间，提前远程抓包和日志取证能显著缩短现场时间。常见错误是故障一出现就重启全部设备，导致日志丢失、根因无法确认。

第 4 步：变更回滚与验证，防止“修好又复发”

若故障前 24 小时内有配置变更（VLAN、ACL、DNS、固件升级），优先在维护窗口回滚验证。回滚前备份当前配置，记录变更前后差异，避免二次故障。验证至少覆盖 3 类终端、2 个网段和 1 个关键业务系统。

修复后连续观察 30–60 分钟，确认丢包率、延迟和业务可用性恢复基线。把根因、处理步骤、影响范围和预防措施写入故障记录，并对同类设备做一次批量检查，减少重复排查。

常见问题

问：Wi-Fi 显示已连接但无法上网，先查什么？

先查本机是否拿到有效 IP 和默认网关，再 ping 网关与公网 IP，最后用 nslookup 测 DNS。三步仍不通，再查 AP 上联与认证日志。

问：只有部分网站打不开，是网络问题吗？

不一定。先对比不同终端与不同 DNS 的解析结果，再查代理、防火墙和 MTU。若仅特定域名失败，优先怀疑 DNS 解析或目标侧策略。

问：间歇性断网没有规律，怎么取证？

做 10 分钟以上连续 ping 记录，同时在网关抓包并导出设备日志，按时间轴对齐。没有取证就重启设备，往往会丢失定位根因的关键信息。
